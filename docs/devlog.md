## Fallback router: a failed LLM call no longer stops the run

*Source: `docs/devlog/2026-10-20-ali-fallback-router.md`*

Date: 2026-10-20
Author: Muhammad Ali

### Observed failure or limitation

On the laptop CPU, LLM calls (`qwen2.5-coder:7b` on Ollama) took 39.1 s on average (`results/initial_results.csv`), close to the 60 s timeout (`llm.timeout_s` in `config.yaml`), and some calls exceeded it. Without handling, a timed-out or malformed answer would raise an exception inside the build, leaving that build with no result, so LLM-relevance could not be compared with DANTE on the same builds.

### Change

- `src/agent/fallback_router.py` sends every shortlisted test through the semantic analyzer and catches timeouts, invalid JSON, schema violations and answers with a confidence below `fallback.min_confidence` (0.3).
- Each failure becomes a `FallbackRecord` (reason, test, latency) that is stored with the build's result.
- With `fallback.scope: build`, one failed call makes the whole build use the DANTE-CCH ranking, so a build always gets a ranking and the comparison stays on the same builds.

### Measured effect

- **Phase 1 run (13 builds):** all 13 builds produced a result. In 4 of them the first call timed out and the build used the DANTE-CCH ranking (`results/initial_results.csv`, row `LLM-relevance`: `llm_fallbacks` 4, `llm_builds_fallen_back` 4).
- **Phase 2:** with one retry added before a fallback (`docs/devlog/2026-11-06-ali-llm-cache.md`) and inference on a GPU (`docs/devlog/2026-11-06-ali-kaggle-gpu.md`), `LLM-relevance` fell back on none of its 132 build-runs on the test split (`results/tables/efficiency.csv`, column `fallback_rate` 0.000).

## Tie order depended on library versions: numpy, pandas and scikit-learn pinned

*Source: `docs/devlog/2026-10-20-bilal-pin-library-versions.md`*

Date: 2026-10-20
Author: Ahmad Bilal (entry written by Muhammad Ali in P2-20 from `docs/dante_notes.md`)

### Observed failure or limitation

Many Karaf tests get the same DANTE score (often 0), and their order comes from pandas' unstable sort. When our DANTE port was first compared with DANTE's stored selections, using numpy 2.5 and pandas 3.0, only 3 of the 50 Phase 1 builds matched the stored 5% selection (`docs/dante_notes.md`, "Known limitations of the shipped code", item 4).

### Change

`requirements.txt` pins the versions of the DANTE package's lock file: numpy 1.26.4, pandas 2.3.2 and scikit-learn 1.7.2. The README tells users to install exactly these.

### Measured effect

- With the pinned versions, 26 of the 50 builds match the stored 5% selection (`docs/dante_notes.md`, item 4; rerun with `python -m src.dante.compare_stored`). That command prints its comparison and writes no file under `results/`, so the 3 → 26 change is recorded only in `docs/dante_notes.md`.
- **Still platform-dependent:** while reviewing run R2 (#70), the non-LLM methods were rerun on a Windows laptop with the same pinned versions. History-only, TF-IDF-only, Tuned-weight (TF-IDF), DANTE-CCH and DANTE-CCH-shipped gave a different tie order than on Kaggle (Linux), with the same candidates, failing tests and durations; Random matched. The local rerun was not committed. All reported results come from Kaggle, where R1, R2 and R3 agree with each other.

## Relevance key mismatch in the shipped DANTE: two DANTE variants

*Source: `docs/devlog/2026-10-20-bilal-two-dante-variants.md`*

Date: 2026-10-20
Author: Ahmad Bilal (entry written by Muhammad Ali in P2-20 from `docs/dante_notes.md`)

### Observed failure or limitation

Our DANTE port with TF-IDF relevance on did not reproduce DANTE's stored scores. In the shipped code, `pipeline_orchestrator.py` stores relevance under the key `"tfidf"`, while `run_selection.py` and `run_prioritization.py` read it under `"bm25"`. The lookup returns 0, so the shipped DANTE-CCH ranks on history only, unlike the paper's description (`docs/dante_notes.md`, item 1).

### Change

Both behaviours are reported as separate methods:
- `DANTE-CCH-shipped`: relevance weight 0, as the shipped code behaves;
- `DANTE-CCH`: TF-IDF relevance on (`1.0·history + 0.5·relevance^1.2`), as the paper describes.

The gap comparisons use `DANTE-CCH` as the base method, and RQ1 also compares with `DANTE-CCH-shipped`.

### Measured effect

- **Phase 1 (13 builds with code changes):** the relevance-off scores reproduce the stored `value_score` of 82–86% of the stored selected tests, and the TF-IDF-on scores only 3–4% (`docs/dante_notes.md`, item 1; rerun with `python -m src.dante.compare_stored --builds subset`, which writes no file under `results/`).
- **Phase 2 test split:** the two variants rank differently. At the 10% budget, mean %DTC is 0.378 for `DANTE-CCH-shipped` and 0.356 for `DANTE-CCH`; mean SAPFDc is 0.264 and 0.274 (`results/tables/main_results.md`).
- **Phase 1 builds:** `DANTE-CCH-shipped` reproduces the replication package's APFDc with a median difference of 0.0000, within 0.02 on 39 of 50 builds (`results/tables/e2_reproduction.md`).

## Evaluation set size: all qualifying builds, 10 dev / 44 test

*Source: `docs/devlog/2026-11-06-ali-eval-set-size.md`*

Date: 2026-11-06
Author: Muhammad Ali

### Observed failure or limitation

The planned Phase 2 evaluation set was 120 builds (20 dev + 100 test), with a rule to stop if fewer than 60 builds qualify (P2-08, PROJECT_CONTEXT §6.2). Applying the fixed filters to the 726 Karaf builds in LRTS left only 54 qualifying builds. Source: `data_eval/eval_set_p2_report.md`, written by `src/data/make_eval_set_p2.py`.
- 626 have at least 100 earlier builds (F1).
- 199 of those change at least one code file (F2).
- 54 of those have a failing test class (F3).
- All 54 have a failing candidate with readable source (F4).

So the 60-build minimum stopped the script before any CSV was written.

The binding constraint is "changes code **and** has a failing test", not the history window. We counted the builds that pass F2 and F3 under shorter history requirements: 57 with at least 50 earlier builds, 60 with at least 10, and 65 with none. These counts were checked before any method was run on these builds.

### Change

Group decision (6 November 2026, option 1 of three): **use every build that passes F1–F4**, with no 60-build minimum and no 120-build target, and keep the chronological split.
- The earliest 10 builds are `dev` and the remaining 44 are `test`. Dev builds date from 2021-05-04 to 2021-06-15, test builds from 2021-08-30 to 2024-04-06.
- The even-spacing pre-selection to 160 builds stays in the script, but applies only when more than 160 builds qualify; with 54 it does not.
- `--n-dev` defaults to 10.
- The rule was fixed before any results were seen, and the script reads no method results.

Changed: `src/data/make_eval_set_p2.py`, `tests/test_eval_set_p2.py` and `docs/PROJECT_CONTEXT.md` §6.2 and §8. The issue bodies that mentioned 100 test builds or 120 builds now say "all test-split builds (44)".

**Why not the other options:**
- **Shorter history window (option 2).** Lowering F1 to 10 earlier builds reaches exactly 60, but it weakens the history signal: DANTE's history score assumes a 100-build window, so the earliest builds would be scored with almost no history, unlike the rest.
- **Dropping the code-change filter (option 3).** This adds builds whose diff touches only file types DANTE ignores. In those builds TF-IDF and LLM relevance have no input, so Gaps 1 and 3 cannot change anything there; the Phase 1 finding was that 37 of 50 builds were of this kind.

### Measured effect

- **Evaluation set:** 54 builds instead of the planned 120 (`data_eval/eval_builds_p2.csv`). The paper's experimental setup and threats to validity must state the smaller test split (44 builds) and the reason.
- **Tuning data:** the dev split for prompt and weight tuning is 10 builds.
- **Phase 1 overlap:** 1 dev build and 10 test builds are also Phase 1 builds (`in_phase1`).

## LLM answer cache, seeds and one retry

*Source: `docs/devlog/2026-11-06-ali-llm-cache.md`*

Date: 2026-11-06
Author: Muhammad Ali

### Observed failure or limitation

Phase 1 inference was slow and fragile. In the 13-build Phase 1 run the LLM made 156 calls with a mean latency of 39.1 s per call, and 4 of the 13 builds fell back to the DANTE ranking because a single call timed out (no retry existed). Every rerun or ablation had to pay for the same calls again, since nothing was cached. Source: `results/initial_results.csv` (row `LLM-relevance`, columns `llm_calls`, `llm_mean_latency_s`, `llm_fallbacks`, `llm_builds_fallen_back`).

### Change

- `src/agent/llm_cache.py`: an on-disk cache keyed by model + prompt + options (temperature, seed, num_ctx) + JSON mode. Only successful calls are stored; entries keep the original latency and token counts, so cost numbers stay real when an answer is reused. Writes are atomic.
- Seeds 1, 2, 3 are part of the key, so repeated runs make their own calls; a retry uses seed + 1000 so it can give a different answer.
- `src/agent/retry.py`: one retry for a timed-out, failed, invalid-JSON or schema-violating call before a `FallbackRecord` is created; the relevance router now uses it.
- Each provider is created for one component and every call record says which component made it and whether it was cached, for the efficiency experiment (E6).

### Measured effect

To be measured in P2-21 (fallback rate, cached-call share and mean latency per component from the run's `per_build.csv`).

## Relevance prompt v2: a calibrated scale with anchors

*Source: `docs/devlog/2026-11-06-ali-relevance-prompt-v2.md`*

Date: 2026-11-06
Author: Muhammad Ali

### Observed failure or limitation

In Phase 1 the LLM gave a relevance of at most 0.2 to 94% of the tests it scored (docs/PROJECT_CONTEXT.md §3, finding 5). So LLM relevance barely changed DANTE's ranking.

The v1 prompt only says "0 = unrelated, 1 = directly tests the changed code". It gives the model no intermediate points and no procedure for comparing the test with the change.

The same measure is taken again for v1 on the dev split (`share_rel_le_0_2` in `results/dev/prompt_comparison.csv`), so that before and after come from the same builds.

### Change

- `src/agent/semantic_analyzer.py`: `PROMPT_TEMPLATE` (v1) is unchanged; a test pins its SHA-256. A new `PROMPT_TEMPLATE_V2` (`"v2"`) differs from v1 in two ways:
  - **Anchors.** It explains the scale with four anchors: 0.0 = unrelated module; 0.3 = same subsystem, different functionality; 0.6 = the test uses a class or package the change touches; 0.9 = the test directly tests a changed class or method.
  - **Comparison step.** It asks the model, before deciding, to compare the test's package, imports and used identifiers with the changed file paths and identifiers.

  The JSON answer shape, the anonymisation and the truncation are the same as v1.
- **Version selection.** `llm_p2.relevance_prompt_version` in the config selects the template. `make_request(..., prompt_version=...)` records it in every `RelevanceRequest` and in `llm_relevance.csv`.
- **Runner option.** `python -m experiments.run_experiment ... --relevance-prompt v1|v2` overrides the config for the two dev runs.
- **Comparison.** `src/agent/prompt_eval.py` compares the two dev runs and applies the decision rule, fixed before the runs: the higher `sapfdc_mean_10` wins; within 0.005, the lower `share_rel_le_0_2` wins.

### Measured effect

Two Kaggle runs on the **dev split only**: 10 builds, seed 1, methods `LLM-relevance` and `DANTE-CCH`. Both ran from commit fbe1b2b on 2 × T4 (`qwen2.5-coder:7b`), with no fallbacks and no failed builds (`results/DEV_prompt_v1/run_meta.json`, `results/DEV_prompt_v2/run_meta.json`). No test-split run was made. The numbers are in `results/dev/prompt_comparison.csv`, written by `python -m src.agent.prompt_eval --runs results/DEV_prompt_v1 results/DEV_prompt_v2`:

| prompt | builds | sapfdc_mean_10 | dtc_mean_10 | share_rel_le_0_2 | share_rel_ge_0_5 | fallback_builds | mean_latency_s |
|---|---|---|---|---|---|---|---|
| v1 | 10 | 0.6725 | 0.7167 | 0.976 | 0.024 | 0 | 3.19 |
| v2 | 10 | 0.6671 | 0.7167 | 0.112 | 0.053 | 0 | 3.40 |

- **Calibration.** v2 does fix the calibration problem. The share of scores at or below 0.2 drops from 97.6% (v1; the Phase 1 problem reproduced on dev) to 11.2%. The share at or above 0.5 rises only from 2.4% to 5.3%, so v2 mostly moves scores to the 0.3 anchor ("same subsystem").
- **Ranking.** This barely changes the ranking. The mean %DTC at 10% is identical (0.7167), and on every dev build each prompt finds the same failing tests. The mean SAPFDc at 10% is 0.0054 lower for v2. Most of that comes from one build, `PR-1377_build4` (0.473 with v1, 0.418 with v2), visible in both runs' `per_build.csv`.
- **Cost.** v2 costs about 7% more latency per call (3.40 s against 3.19 s) because its prompt is longer.

**Decision**, by the rule fixed before the runs: the higher `sapfdc_mean_10` wins unless the two are within 0.005. The difference is 0.0054, above the margin, so **v1** is chosen, and `relevance_prompt_version` stays `v1` in `config.yaml`.

The better calibration of v2 is therefore not used for the reported results. That is a negative result for this prompt change, reported as measured. P2-11 uses `results/DEV_prompt_v1/llm_relevance.csv` (the chosen prompt's dev scores).

## Explainer: explain only important skipped tests, with cited evidence

*Source: `docs/devlog/2026-11-06-bilal-explainer.md`*

Date: 2026-11-06
Author: Taha Bashir

### Observed failure or limitation

Gap 2 says explanations for test selection have only been shown on a small synthetic system. RQ2 (docs/PROJECT_CONTEXT.md §8) is supported only if (a) the decision and explanation time stays below the test time saved, and (b) at least 80% of 100 sampled justifications are rated *sound*: every factual statement is supported by the evidence the explainer was given, and the reason for skipping follows from that evidence. An explainer that writes free text about every skipped test would fail both conditions: a Karaf build has hundreds of skipped candidates (one LLM call each is far too slow), and an LLM asked to "explain" without fixed evidence tends to add facts it was never given, which a rater must mark unsound.

### Change

`src/agent/explainer.py` (prompt version `e1`):

- **Only important skipped tests.** `select_skipped` keeps skipped tests that are among the top 20 candidates by history score or by relevance (`explainer.candidate_pool`), in ranking order, at most 5 per build and budget (`explainer.top_n_skipped`). These are the skips a developer would question; a test with no failures and no relevance needs no explanation. This bounds the cost to at most 5 calls (10 with retries) per build and budget, independent of the suite size.
- **Fixed evidence, cited.** `build_evidence` gives the model a small JSON object: history statistics from the `history_retrieval` tool, the history score and relevance used, the semantic analyzer's reason, the changed files, and why the budget excluded the test (budget left when the greedy scan reached it, and the budget at which it would have fitted). The prompt says to use only these facts and to copy the facts it used into `cited_facts`. The evidence is stored with every `ExplanationRecord`, so raters judge each justification against exactly what the model saw.
- **Validation and retry.** Answers are validated against `explanation_response` (at most 400 characters, 1–6 cited facts, the right test name) and retried once; a second failure gives `ok=False` with the reason, and selection is never affected.
- **Grounding check.** `grounding_report` checks automatically that the numbers and file names in each cited fact appear in the evidence. It is reported next to the human rating and does not replace it.
- The explainer never reads the target build's outcomes; a test runs it with opposite outcome columns and with no outcome column and gets identical prompts and evidence.

### Measured effect

To be measured in P2-21 (R1, `Full system`, seed 1): explainer calls, latency and success rate from `per_build.csv` (`explainer_calls`, `explainer_latency_s`, `explainer_ok`) against `time_saved_s`, and the share rated sound in P2-24/P2-25 (`results/gap2/rating_summary.md`).

## Orchestrator prompt: o1 copied its example, o2 decides per build

*Source: `docs/devlog/2026-11-07-ali-orchestrator-prompt.md`*

Date: 2026-11-07
Author: Muhammad Ali

### Observed failure or limitation

Issue #6 fixes a rule for the orchestrator prompt: run `Agent-weighted` on the **dev split** (seed 1), and improve the prompt if the orchestrator falls back on more than 20% of builds or gives the same w for every build.

With prompt **o1**, the dev run `DEV_orch_o1` (Kaggle, commit a11b865, 10 builds) gave **w = 0.5 with confidence 0.8 on every build**. It made no tool calls, took one step each time and never fell back. These are exactly the values of the example final answer in the o1 prompt (`{"action": "final", "w": 0.5, "confidence": 0.8, ...}`): the model copied the example instead of deciding per build. The rule is triggered (`rule_triggered = True` in `results/dev/orchestrator_prompt_iterations.csv`). With a constant w, Agent-weighted is not a per-build decision at all; it is a fixed weight of 0.5.

### Change

Prompt **o2** (`src/agent/orchestrator.py`, `PROMPT_TEMPLATE_O2`; `ORCH_PROMPT_VERSION = "o2"`):
- **Placeholders only.** The answer shapes contain no numbers the model could copy: `"w": <your weight for this build, from 0 to 1>`. Neither the o1 example values nor DANTE's 0.67 appear in the instructions; the only numbers are the 0–1 range and the formula's exponent 1.2. A test checks this.
- **Guidance.** The prompt explains which build features should lower w (a strong, specific relevance signal and a focused change) and which should raise it (flat or weak relevance, informative history). It says builds differ and should usually get different w, and it asks for a reason naming the deciding features.
- **Selection.** `orchestrator.prompt_version` in `config.yaml` and `config_kaggle.yaml` now selects the template (o1 stays available for the record), and `run_meta.json` records the version that actually ran.

**One o2 attempt ran o1 by mistake.** The first o2 run on Kaggle used o1, because `config_kaggle.yaml` still said `prompt_version: o1`. `run_meta.json` recorded o1, and the decisions repeated o1's w = 0.5 / confidence 0.8 on all 10 builds. That repeat is not committed, but it shows that o1's behaviour reproduces in a second session. The config was fixed, and a new test checks that `config_kaggle.yaml` differs from `config.yaml` only in paths. A later rerun into the same run folder was skipped by `--skip-existing`, and that zip was discarded too: its merged `run_meta.json` claimed o2 while its rows were o1 data, and only its `git_commit_warning` showed the mix. The committed o2 run was made from a cleared folder.

### Measured effect

Dev split, 10 builds, seed 1; both runs on Kaggle. The numbers come from `results/dev/orchestrator_prompt_iterations.csv`, written by `python -m src.agent.orchestrator_eval --runs results/DEV_orch_o1 results/DEV_orch_o2`:

| prompt | run | fallback rate | distinct w | w min / mean / max | mean confidence | tool calls per build | SAPFDc@10%: Agent-weighted | LLM-relevance | DANTE-CCH | rule triggered |
|---|---|---|---|---|---|---|---|---|---|---|
| o1 | DEV_orch_o1 (a11b865) | 0.0 | 1 | 0.5 / 0.50 / 0.5 | 0.80 | 0.0 | 0.6770 | 0.6725 | 0.5530 | yes |
| o2 | DEV_orch_o2 (6d620f2) | 0.0 | 5 | 0.2 / 0.47 / 0.8 | 0.76 | 0.0 | 0.6656 | 0.6725 | 0.5530 | no |

- **The rule is satisfied.** o2 gives varied w (0.2, 0.3, 0.5, 0.7, 0.8) and never falls back, so the iteration stops at o2, as the rule in issue #6 says. o2 is the prompt for the runs.
- **Ranking on dev.** o2's per-build weights rank slightly worse on dev than o1's constant 0.5: Agent-weighted SAPFDc@10% is 0.6656 against 0.6770. LLM-relevance (fixed w = 2/3) is 0.6725. The rule does not choose by SAPFDc, and was not changed after seeing these numbers.
- **Remaining weaknesses, for the failure analysis (P2-14) and the paper:**
  - Several o2 reasons point the wrong way. For example, "Low relevance signal and weak history indicate a need to trust relevance more" comes with w = 0.3, while the prompt says weak relevance should raise w.
  - o2 still never calls a tool.
  - The feature list in the prompt still describes `n_rel_ge_05` as "relevance >= 0.5" (shared with o1), so one copyable number remains in the build data shown to the model.
- **Test split.** No test-split run was made for this choice.

  - The model answered 43 of 44 builds in every seed (`ranking_source` = `llm`): one call per build, latency 95.6–226.3 s, median about 181 s.

  - `llm_relevance.csv` has one row per candidate for the 43 answered builds (8,484 rows) and no fell-back rows. `reason` and `confidence` are empty, because the single-call answer only gives scores.

  - %DTC, `DANTE-CCH-shipped` vs `DANTE-CCH (stored)`: median difference 0.000, equal on 136 of 150 build-budget pairs.

### What went wrong

1. **`Single-call LLM` timed out on every build in the first attempt.** The single-call provider used `llm.timeout_s: 60`, which is shorter than generating scores for about 200 candidates on a T4. All 132 rows per seed were DANTE fallbacks.
   - Fix (#62, merged in #64): a separate `single_call.timeout_s`.
   - Its value, 480 s, was set from a timing run on 10 **dev** builds (`results/DEV_single_call_timing/`, slowest call 225.8 s). The timings of the failed test run were not used.
2. **`DANTE-CCH (stored)` rows were missing** from the first `E2_stored_phase1_seed1` (300 rows instead of 450), because `make_components` never set the stored loader. Fixed in #62/#64.
3. **The interactive Kaggle session kept `/kaggle/working` from an earlier session.**
   - The Python environment cell failed because `.venv` already existed. It was rerun with `uv venv --clear`.
   - The old `results/E2_stored_phase1_seed1/` folder was deleted before the run, so that `--skip-existing` could not reuse old rows; `skipped_existing` is empty.

Because of the fixes, E1 and E2_stored use commit `e63cf0b` and not the R1 commit `45e4496`. Apart from result files, trace samples, a devlog and tests, the two commits differ only in the two fixes (`experiments/run_experiment.py` and the `single_call.timeout_s` key in `config.yaml` and `config_kaggle.yaml`), and the non-LLM rows are identical on both commits.
